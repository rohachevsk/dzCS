# 10.11 (Classwork) — Керування пам'яттю та Garbage Collector у .NET

Класворк присвячений дослідженню роботи автоматичного збирача сміття (**Garbage Collector**, GC) у середовищі CLR / .NET, життєвому циклу об'єктів, поколінням купи пам'яті (Gen 0, Gen 1, Gen 2, LOH) та аналізу ефективності виділення пам'яті.

---

## Структура проєкту

- **`DataProcessor.cs`** — реалізація класу `DataProcessor` для обробки великих масивів даних із завдання, а також допоміжний клас `FinalizableResource` із фіналізатором для тестування `WaitForPendingFinalizers`.
- **`Task1_MemoryAnalysis.cs`** — виконання коду із завдання 1, аналіз поколінь об'єктів та детальні теоретичні відповіді.
- **`Task2_GcDemo.cs`** — практична демонстрація методів `GC.GetTotalMemory()`, `GC.Collect()`, `GC.GetGeneration()`, `GC.CollectionCount()`, `GC.WaitForPendingFinalizers()`.
- **`Task3_Experiment.cs`** — стрес-тест із виділенням 10 000 об'єктів розміром 100 KB, порівняння пам'яті до та після збирання, аналіз спрацьовувань GC по поколіннях.
- **`Program.cs`** — точка входу з інтерактивним консольним меню.

## 1. Аналіз пам'яті

### Вихідний код:
```csharp
public class DataProcessor
{
    private byte[] _buffer;

    public DataProcessor(int size)
    {
        _buffer = new byte[size];
    }

    public void Process()
    {
        // Імітація обробки даних
    }
}

public static void Main()
{
    for (int i = 0; i < 1000; i++)
    {
        var processor = new DataProcessor(1024 * 1024);
        processor.Process();
    }

    Console.WriteLine($"Memory: {GC.GetTotalMemory(false)}");
}
```

### Відповіді на запитання:

#### 1. Що відбувається з об'єктами після кожної ітерації?
- На кожній ітерації циклу створюється новий екземпляр класу `DataProcessor`, і в купі виділяється буфер `new byte[1024 * 1024]` (1 МБ).
- Посилання на об'єкт зберігається в локальній змінній `processor`.
- Коли ітерація завершується (або потік виконання переходить до наступного кроку циклу), змінна `processor` виходить з області видимості, і посилання на об'єкт перетирається.
- Об'єкт `DataProcessor` та його масив `_buffer` втрачають кореневе посилання (**GC Root**) і стають **недосяжними (unreachable / "мертвими")**.
- Вони продовжують перебувати в керованій купі пам'яті (managed heap) як сміття доти, доки GC не виконає черговий цикл очищення.

#### 2. Чому пам'ять не обов'язково звільняється одразу після завершення ітерації?
- Керування пам'яттю в .NET є **недетермінованим (non-deterministic)**: вихід змінної з області видимості не викликає автоматичного або миттєвого звільнення оперативної пам'яті (на відміну від деструкторів на стеку в C++).
- Збирання сміття є ресурсомісткою операцією, яка включає фази:
  1. **Marking (маркування):** обхід графа живих об'єктів від коренів (GC Roots).
  2. **Sweeping / Compacting (підмітання / стиснення):** звільнення пам'яті та дефрагментація купи.
- Якби CLR запускав збирання сміття після кожної ітерації, це спричинило б катастрофічне падіння продуктивності (**throughput penalty**) через часті зупинки потоків виконання (**Stop-the-World pauses**).
- GC запускається **лише за певних умов**:
  - Вичерпано ліміт виділення (allocation budget) для відповідного покоління;
  - Операційна система повідомляє про брак фізичної пам'яті (low-memory notification);
  - Було викликано явний метод `GC.Collect()`.

#### 3. Які покоління GC існують у .NET?
Платформа .NET базується на **гіпотезі поколінь (generational hypothesis)**: більшість об'єктів живуть дуже короткий час. Керована купа розділена на такі сегменти:
- **Покоління 0 (Gen 0):** містить щойно створені, короткоживучі об'єкти (локальні змінні, тимчасові масиви/рядки). Очищення Gen 0 відбувається найчастіше і є найшвидшим.
- **Покоління 1 (Gen 1):** буферне покоління між короткоживучими та довгоживучими даними. Об'єкти, що вижили під час збирання Gen 0, переміщуються в Gen 1.
- **Покоління 2 (Gen 2):** довгоживучі об'єкти (статичні поля, глобальні екземпляри, кеші, об'єкти з довгим часом життя). Збирання Gen 2 (відоме як **Full GC**) зачіпає всі покоління і є найважчим для процесора.
- **Спеціальні сегменти:**
  - **LOH (Large Object Heap):** окремий сегмент купи для великих об'єктів (за замовчуванням $\ge 85\,000$ байт). Через високу вартість копіювання LOH за замовчуванням не дефрагментується, а його очищення прив'язане до збирання Gen 2.
  - **POH (Pinned Object Heap, з .NET 5):** для закріплених у пам'яті об'єктів.
  - **Frozen Object Heap / Non-GC Heap (з .NET 8):** сегмент для статичних та незмінних об'єктів, які взагалі не перевіряються GC.

#### 4. До якого покоління потраплятимуть створені об'єкти?
У наведеному коді об'єкт складається з двох сутностей:
1. **Сам екземпляр `DataProcessor`:** це невеликий об'єкт (посилання на `_buffer` + метадані заголовка об'єкта та таблиці методів, розмір 24–32 байти на x64). Він потрапляє у **Покоління 0 (Gen 0)**.
2. **Внутрішній масив `_buffer = new byte[1024 * 1024]`:** розмір становить **1 048 576 байт (~1 МБ)**, що на порядок перевищує поріг $85\,000$ байт. Тому масив виділяється **безпосередньо у LOH (Large Object Heap)**.
3. Оскільки LOH обслуговується разом із Поколінням 2, метод `GC.GetGeneration(processor.Buffer)` повертає **2**.
4. **Наслідок:** виділення великих масивів у кожній ітерації змушує GC постійно ініціювати збирання **Gen 2 / LOH**, що спричиняє високе навантаження на систему. Для таких сценаріїв у сучасному C# рекомендується використовувати пул буферів (`ArrayPool<byte>.Shared`).

## 2. Робота з GC (демонстрація методів)

У класі `Task2_GcDemo.cs` наведено приклади використання ключових методів:

| Метод | Призначення | Поведінка в демо |
|---|---|---|
| `GC.GetTotalMemory(bool forceFullCollection)` | Повертає обсяг пам'яті (в байтах), виділеної в керованій купі. | Вимірюється до створення тимчасових об'єктів, після виділення (~20 МБ) та після очищення. |
| `GC.Collect()` | Примусово запускає повне збирання сміття у всіх поколіннях. | Звільняє недосяжні об'єкти та суттєво зменшує показник `GetTotalMemory`. |
| `GC.GetGeneration(object obj)` | Повертає поточний номер покоління (0, 1 або 2), де знаходиться об'єкт. | Демонструє еволюцію довгоживучого об'єкта: $0 \to 1 \to 2$ після серії викликів `GC.Collect()`. Також показує, що великий масив одразу потрапляє у покоління 2 (LOH). |
| `GC.CollectionCount(int generation)` | Повертає кількість збирань, виконаних для вказаного покоління від старту процесу. | Фіксуються та порівнюються значення лічильників для Gen 0, Gen 1, Gen 2 до та після навантаження. |
| `GC.WaitForPendingFinalizers()` | Блокує поточний потік доти, доки окремий потік фіналізації не завершить виконання методів `Finalize()` (~деструкторів). | Демонструє, що після `GC.Collect()` фіналізатори можуть не встигнути виконатися, а `WaitForPendingFinalizers()` гарантує завершення їх роботи. |

## 3. Практичний експеримент (10 000 об'єктів по 100 KB)

### Умови:
- Створюється 10 000 об'єктів `DataProcessor`, кожен з буфером розміром $100 \text{ KB} = 102\,400$ байт.
- Загальний теоретичний обсяг виділеної пам'яті: $10\,000 \times 102\,400 \approx 1\,024\,000\,000$ байт (~**976.56 МБ**).

### Результати вимірювань:

| Показник | До виклику GC | Після GC.Collect() |
|---|---|---|
| **Використання пам'яті** | ~1.94 МБ (актуальний залишок незібраної купи) | ~0.08 МБ (базовий стан) |
| **Кількість запусків GC Gen 0** | 522 | 524 |
| **Кількість запусків GC Gen 1** | 522 | 524 |
| **Кількість запусків GC Gen 2 (LOH)** | 521 | 523 |
| **Звільнено пам'яті** | — | **~1.86 МБ** |

### Висновки з експерименту:
1. **Поведінка LOH:** об'єкти розміром 100 KB (> 85 KB) виділяються виключно в Large Object Heap. Тому кожен раз, коли вичерпується бюджет LOH, GC ініціює повне збирання сміття (Gen 2). Саме тому кількість збирань Gen 2 зросла практично настільки ж, як і Gen 0 / Gen 1 (~324 збирання за час експерименту).
2. **Звільнення пам'яті:** оскільки об'єкти локальні і посилання на них не зберігаються, після виклику `GC.Collect()` пам'ять практично повністю очищується (зменшується до початкових 0.08 МБ).
3. **Оптимізація:** для уникнення навантаження на Gen 2 і фрагментації LOH у реальних високонавантажених проєктах слід уникати частого створення великих тимчасових масивів та застосовувати `System.Buffers.ArrayPool<T>` або `MemoryPool<T>`.
